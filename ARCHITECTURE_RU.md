# Архитектура HibpGuard

Интерфейс отвечает за отображение и ввод. ViewModel хранит состояние конкретной проверки и управляет её жизненным циклом. Сервисы выбирают способ проверки, а `HIBPClient` собирает HTTP-запросы и разбирает ответы. Благодаря протоколам сервис и транспорт можно заменить в тестах без реальных запросов.

## Структура папок

| Папка | Файлы и назначение |
|---|---|
| `HibpGuard/App` | `HibpGuardApp`, `AppContainer`, `RootView`: точка входа, создание зависимостей, вкладки и обработка ухода в фон |
| `HibpGuard/Models` | `Breach`, `CheckState`, `AppError`, `ActionStep`: данные и состояния |
| `HibpGuard/Networking` | `HTTPTransport`, `HIBPClient`, `CheckServices`, `PasswordFingerprint`, `PasswordRangeParser`: сеть и локальное сравнение хэшей |
| `HibpGuard/ViewModels` | `EmailCheckViewModel`, `PasswordCheckViewModel`, `SettingsViewModel`: состояние экранов на `MainActor` |
| `HibpGuard/Views` | Экраны email, пароля, плана, настроек и общие элементы интерфейса |
| `HibpGuard/Storage` | `KeychainAPIKeyStore` для ключа; `ActionPlanStore` и `FileChecklistStorage` для отметок |
| `HibpGuardTests` | Тесты сетевого контракта, обработки паролей, ViewModel и хранилищ |
| `Tools` | Запуск тестов в симуляторе и воспроизводимый генератор `.xcodeproj` |
| `.github/workflows` | Ручной запуск проверки на macOS runner |

## Поток данных

| Сценарий | На устройстве | Через сетевую границу | Обратно в интерфейс |
|---|---|---|---|
| Email в HIBP API | ViewModel проверяет формат; сервис читает личный ключ из Keychain | В HIBP уходят email и заголовок с ключом | Клиент декодирует `[Breach]`; ViewModel публикует результат или ошибку |
| Email в деморежиме | Сервис возвращает вымышленные данные | Ничего | Экран явно показывает, что результат демонстрационный |
| Пароль | ViewModel вычисляет SHA-1 из точных UTF-8-байтов и очищает поле | В Pwned Passwords уходит пятисимвольный префикс | Клиент локально находит суффикс, в UI возвращается только число |
| Чек-лист | Store меняет набор стабильных идентификаторов | Ничего | Небольшой JSON сохраняется атомарно; отметка меняется после успешной записи |

## Почему так

`@MainActor` у ViewModel позволяет менять UI-состояние на главном акторе. `URLSession` выполняет ожидание сети асинхронно. SHA-1 вычисляется один раз после нажатия кнопки, без запросов по мере ввода. Сырой пароль не передаётся в асинхронный сервис: тот принимает `PasswordFingerprint`.

Один `CheckState` делает состояния ожидания, загрузки, успеха и ошибки взаимоисключающими. Сетевая ошибка не может автоматически превратиться в число 0 или пустой список. Разбор range-ответа строгий: повреждённые строки и HTML-страницы вызывают ошибку.

У каждой проверки есть идентификатор запроса. Изменение ввода и отмена делают старый идентификатор неактуальным. Даже если сервис проигнорирует отмену и позднее вернёт ответ, ViewModel его не опубликует. Это отдельно проверяется тестами.

Транспорт использует ephemeral-сессию без cookies и URLCache. Редиректы не выполняются, чтобы пользовательский заголовок с ключом не попал на другой адрес. В приложении нет логирования запросов и сторонней аналитики. Сообщения об ошибках не включают URL или произвольный текст сетевой ошибки.

API-ключ обновляется в Keychain через `SecItemUpdate`, без предварительного удаления старого значения. Ошибка записи не должна уничтожать уже сохранённый ключ. Настройки показывают только факт наличия ключа и не подставляют его обратно в поле.

Чек-лист хранит только идентификаторы действий. Там нет аккаунтов, паролей и истории проверок, поэтому для него выбран JSON, а не Keychain. Это общий план: перед работой с новой утечкой пользователь сбрасывает отметки.

После ухода приложения из активного состояния отменяются запросы и очищаются поля с email, паролем и новым API-ключом. Это не обещание гарантированно обнулить все копии Swift String в оперативной памяти. При повторном открытии приложение читает сохранённые отметки плана.

Для MVP нет фонового мониторинга, автоматического повтора запросов и аккаунта пользователя. Ответ 429 задаёт срок, до которого кнопка реального запроса недоступна; повтор запускает сам пользователь. Изменение email не сбрасывает этот срок.
